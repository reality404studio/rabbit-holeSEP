# 오프라인 지도

페이블이 SEP 목차 1,859항목을 **한 번** 읽고 만드는 좌표계.
한 번 만들면 리포에 커밋되고, 질의 시점에는 이 지도만 읽는다.

## 왜

지금은 질문 하나당 목차 32,645토큰이 통째로 모델에 들어간다.
페이블 비용의 **73%가 목록 읽기이고 27%만 사고**다. 비싼 자원을 싼 일에 쓰고 있다.

지도가 생기면 그 비율이 뒤집힌다. 그리고 아낀 몫으로
`output_config.effort`를 올릴 수 있다 — 지금보다 싸면서 페이블이 더 생각한다.

## 두 층인 이유

**1층 분야(fields)** 는 코퍼스를 덮는다. 검색용. 모든 항목이 하나씩 배정된다.

**2층 문제축(axes)** 은 분야를 가로지른다. **이게 지도를 만드는 진짜 이유다.**
같은 분야 안의 연결은 뻔하다. 서로 멀리 떨어진 분야의 두 항목이 같은 문제축을
공유할 때 의외의 연결이 나오고, 그게 `api/match/route.ts` 가 모델에게 요구하는
바로 그것이다 — *"어떤 의외의 연결 또는 통찰적 frame이 잡혔고"*.

분야 분류만 있으면 이 서비스는 그냥 카테고리 검색이 된다.

## 절차

| | 프롬프트 | 입력 | 출력 | 횟수 |
|---|---|---|---|---|
| 1 | `PROMPT-1-분류체계.md` | `entries-all.txt` | `fields.json` | 1회 |
| 2 | `PROMPT-2-배정.md` | `fields.json` + `batches/NN.txt` | `assign.jsonl` | 10회 |

2단계는 **배치마다 새 대화**로. 긴 대화에서는 앞 배치의 판단이 뒤를 오염시킨다.
10개 배치의 출력을 순서대로 이어 붙여 `map/assign.jsonl` 로 저장한다.

## 검사 — 사람이 "다 됐다"고 하기 전에

```
node map/validate.mjs map/fields.json map/assign.jsonl
```

손으로 붙여넣은 10배치는 반드시 어딘가 빠진다. 검사기가 잡는 것:

- 배정 안 된 항목 (배치 출력이 잘린 경우 — **가장 흔하다**)
- 중복 배정 · 분류 체계에 없는 id · 깨진 JSON
- 항목이 하나도 없는 분야
- 120개를 넘는 분야 (후보 추출에 쓰기엔 너무 크다)
- **3개 분야에 못 걸친 문제축** — 그건 축이 아니라 하위 주제다

마지막 항목이 중요하다. 축이 한 분야 안에만 있으면 2층을 만든 의미가 없다.

## 지어냄에 대해

페이블도 1,859개를 다 알지는 못한다. 인명 항목, 비서구 전통, 도치되어 잘린
제목(`atomism-modern :: 17th to 20th century`)이 특히 그렇다.

그래서 배정 스키마에 `c`(확신도)가 있다. 프롬프트는 모를 때 그럴듯한 설명을
쓰지 말고 `l` 로 표시하라고 지시한다. `l` 비율이 낮게 나오면 그건 좋은 신호가
아니라 **의심할 신호다** — 진짜로 다 알거나, 확신도를 부풀렸거나 둘 중 하나다.
검사기가 그 비율을 출력한다.

## 다음

지도가 통과하면 `api/match/route.ts` 를 2단계로 바꾼다:

1. 질문 + `fields.json`(작다) → 페이블이 분야 2~4개와 문제축 0~3개를 고른다
2. 고른 분야·축에 걸린 항목만 후보로 꺼낸다
3. 후보 + 질문 → 페이블이 큐레이션 (지금 하던 일)

1·3 모두 페이블이고, 목차 전체는 어느 쪽에도 안 들어간다.
