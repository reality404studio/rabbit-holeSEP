# 한글 조판 원칙 — 스킬 초안

Rabbithol.SEP 리디자인(2026-08) 과정에서 추출. **아직 스킬이 아니다.**
스킬로 만들기 전에 다른 프로젝트에서 한 번 더 검증해야 할 것들이 섞여 있다(맨 아래 「검증 안 된 것」 참조).

각 항목에 근거를 표시한다:

- **[출처]** 외부 문헌. 링크는 맨 아래
- **[측정]** 이 세션에서 브라우저로 직접 잰 값. 재현 방법 있음
- **[경험]** 실제로 깨져서 고친 것. 근거는 있으나 문헌으로 확인하진 않음
- **[판단]** 위 셋에서 끌어낸 내 해석. 가장 약한 근거

## 0. 이 문서를 관통하는 한 문장

> **한글은 전각 상자를 채우고, 라틴은 베이스라인 위에 놓인다.**

CSS의 기본값(`line-height`, `letter-spacing`, `align-items`, `word-break`, `overflow-wrap`)은
전부 라틴을 전제로 설계됐다. 한글 조판이 어색해지는 거의 모든 경우가 이 한 문장에서 파생된다.

> 라틴 알파벳은 베이스라인을 기준으로 글자가 나열되지만 한글은 전각 상자를 기준으로
> 가운데에 글자의 무게중심이 실려 있습니다. **[출처: Adobe 폰트 페어링 가이드]**

## 1. 줄바꿈 — 가장 먼저 확인할 것

### 규칙

```css
body{
  word-break: keep-all;      /* 어절 단위로만 끊는다 */
  line-break: strict;
  overflow-wrap: normal;     /* ★ 반드시 normal */
}
/* 끊을 곳이 없는 기계 문자열에만 예외 */
.url, .mono{ overflow-wrap: anywhere; }
```

### 왜 `overflow-wrap: normal`인가 **[측정]**

`keep-all`과 `overflow-wrap: break-word`를 **같이 걸면 후자가 이긴다.**
칸이 좁아지는 순간 keep-all을 무시하고 어절을 쪼갠다. 좁은 상자에서 실측:

| 설정 | 결과 |
|---|---|
| `keep-all` + `break-word` | 먹었습니**/**다, 만들어졌**/**는지가, 계산주의**/**적 |
| `keep-all` + `normal` | 먹었습니다 / 만들어졌는지가 / 계산주의적 |
| `keep-all` + `anywhere` | 쪼개짐 |

여러 블로그가 "`word-break: break-all`과 `overflow-wrap: break-word`를 같이 쓰라"고
권하는데, **한글에는 정반대다.** 그 조언은 라틴/URL 기준이다. **[출처 + 판단]**

대가: 아주 좁은 칸에서 긴 어절이 상자를 넘칠 수 있다. 어절을 쪼개는 것보다 낫다. **[판단]**

### 금칙 처리 **[출처: W3C klreq]**

CSS `line-break: strict`가 일부를 처리하지만 완전하지 않다.

- 줄 첫머리에 올 수 없음: 닫는 괄호, 하이픈, 중점, 마침표·쉼표, 반복 기호, 장음 기호
- 줄 끝에 올 수 없음: 여는 괄호
- 끊으면 안 되는 묶음: 연속된 줄표·말줄임표·아라비아 숫자

따옴표가 든 문장(`'기계가 마음을 가질 수 있는가'`)이 있으면 육안으로 한 번 확인할 것.

## 2. 자간 — 폰트 세대에 따라 방향이 다르다

### 규칙 **[출처: 인디자인 본문 조판 팁 · 한글 타이포그래피 안내서]**

> 옛날에 만들어진 한글 서체는 **정사각형 모듈**에 맞춰 만든 게 많아 자간을 많이 줄여야 하지만,
> **최근에 제작된 폰트들은 굳이 줄이지 않아도 괜찮습니다.**

| 폰트 성격 | 예 | 본문 자간 |
|---|---|---|
| 정사각 모듈 계열(구세대) | Nanum Myeongjo, 바탕 | `-0.015 ~ -0.025em` |
| 최근 폰트(자족폭 좁음) | Hahmlet, Pretendard | `0 ~ -0.01em` |

최근 한국 폰트는 글자 폭을 **850–950 units**로 좁게 뽑는 추세라 이미 좁다. **[출처: Typotheque]**

### 이 세션에서 한 실수 **[경험]**

v8에서 Hahmlet(2021년 폰트)에 `-0.03em`을 줬다. **방향이 반대였다.**
v9에서 Nanum Myeongjo로 바꾸면서 비로소 음수 자간이 정당해졌다.
→ **폰트를 바꾸면 자간 정책도 같이 바꿔야 한다.** 토큰만 옮기면 안 된다.

### 크기별로 나눌 것

자간은 하나의 값이 아니라 크기의 함수다. 작을수록 덜 조인다(0에 가깝게).
13px 이하 한글을 음수 자간으로 조이면 판독이 무너진다. **[판단]**

## 3. 행간 — 라틴 기준값을 그대로 쓰지 말 것

**[출처: Typotheque / Google Fonts CJK · W3C klreq]**

> CJK 텍스트는 글자당 정보 밀도가 높아 **1.7 내외**의 행간이 가독성과 균형을 함께 개선한다.

W3C klreq는 예시로 **160%**를 든다. 안그라픽스 계열 자료는 **1.4~2.0배**를 든다.

| 역할 | 권장 |
|---|---|
| 본문 | 1.7 ~ 1.8 |
| 부제·소제목 | 1.45 ~ 1.55 |
| 제목 | 1.3 ~ 1.45 |
| 대형 디스플레이 | 1.15 ~ 1.25 |

### 이 세션에서 한 실수 **[경험]**

본문만 1.75로 맞춰놓고 제목은 전부 라틴 값(1.16 / 1.28 / 1.35 / 1.45)이었다.
한글 제목은 받침 때문에 세로 공간을 더 먹는다. 큰 글자에서 1.1은 윗줄 받침과 아랫줄 초성이 붙는다.

## 4. 혼식 — 한글과 라틴이 한 줄에 있을 때  ★핵심

### 4-1. 폰트 스택 **순서**가 결과를 바꾼다 **[경험]**

```css
/* ✗ 한글 폰트가 앞 — 라틴 글리프까지 한글 폰트가 그린다 */
--prose: "Nanum Myeongjo", "Old Standard TT", serif;

/* ✓ 라틴 폰트가 앞 — 라틴은 라틴 폰트, 한글은 폴백으로 한글 폰트가 받는다 */
--prose: "Old Standard TT", "Nanum Myeongjo", serif;
```

한글 폰트 대부분이 **라틴 글리프를 포함한다.** 스택 앞에 두면 문장 속 `SEP`, `AI` 같은
라틴이 한글 폰트의 라틴으로 그려진다. 그런데 제목·라벨은 진짜 라틴 폰트로 그려지니
**한 지면에 라틴 활자가 두 종류** 생긴다. v8의 실제 문제였고, 눈으로는 "뭔가 안 맞는다"로만 느껴진다.

### 4-2. 라틴을 약 105% 키운다 **[출처: Adobe]**

> 그대로 타입세팅하면 **라틴 알파벳이 한글보다 아래로 내려앉은 것 같은 느낌**을 줄 수 있으며 (…)
> 대체로 라틴 알파벳을 한글의 **105% 정도 크게** 지정하지만, 폰트와 사이즈에 따라 다르므로
> 그때그때 시각적으로 맞춰야 합니다.

```css
.lat{ font-family: var(--la); font-size: 1.05em; letter-spacing: 0; }
```
```html
<p>편집자는 답을 대신 쓰지 않습니다. <span class="lat">SEP</span>&nbsp;원문으로 …</p>
```

**105%는 출발점이지 정답이 아니다.** 폰트 조합마다 재야 한다(§7).

### 4-3. 대형 텍스트에서는 105%로 어림도 없다 **[측정]**

같은 `font-size`라도 실제 보이는 잉크 높이가 다르다. 직접 잰 값:

| | em 대비 잉크 |
|---|---|
| Old Standard TT 대문자 | **0.73em** (캡높이~베이스라인만) |
| Nanum Myeongjo 한글 | **0.945em** (ascent 0.828 + descent 0.117) |

→ 같은 크기에서 **한글이 29% 커 보인다.**

실제 사고: 제호를 42px로 지정했는데 보이는 글자는 **30.7px**. 그 옆 **12px 한글 두 줄
블록이 30.6px**. 둘이 똑같아서 "가운데가 오목하다"는 인상이 됐다.
제호는 64px까지 키워야 캡높이 47px = 한글 블록의 1.5배가 됐다.

**교훈:** 본문 혼식은 x-height 대 한글 잉크 비교라 105%로 충분하지만,
**대문자 제목은 캡높이 대 한글 블록 비교라 보정이 훨씬 커야 한다.** **[판단]**

### 4-4. 라틴용 유틸리티 클래스 안에 한글을 넣지 말 것 **[경험]**

```css
.la{ letter-spacing: .14em; text-transform: uppercase; }
```

이 안에 한글이 들어가면 **한글이 0.14em 자간을 상속받아 낱글자로 흩어진다.**
v8에서 `.wing em`, 출처줄의 한글 칸, 콜로폰(.2em), 편집자 코멘트가 전부 그랬다.

→ **`.la` / `.mo`는 라틴 전용, `.ko`는 한글 전용으로 분리하고 마크업에서 span을 나눈다.**
"한 요소 안에 두 문자 체계를 넣고 CSS로 어떻게든 해보려는 시도"가 근본 원인이다.

### 4-5. 조사는 라틴에 붙여 쓰고, 묶어서 끊기게 한다

W3C klreq: **라틴 단어 뒤에 한국어 조사가 올 때 사이에 공백을 두지 않는다.** **[출처]**

그리고 `SEP 원문`처럼 라틴+한글이 한 덩어리로 읽히는 경우, 사이를 `&nbsp;`로 묶는다.
안 그러면 `SEP`이 줄 끝에 홀로 남는다. **[경험]**

### 4-6. `palt`를 본문에 걸지 말 것 **[경험 + 판단]**

`font-feature-settings: "palt" 1`은 **일본어 조판용 비례 자간 조정**이다.
한글 15px 본문에 걸면 자간이 들쭉날쭉해진다. 큰 글자(디스플레이)에만.

## 5. 정렬 — CSS는 박스를 맞추지 글자를 맞추지 않는다

### 원리 **[측정]**

`align-items: end / center / baseline`은 **박스**를 정렬한다. 그런데

- 한글은 전각 상자를 거의 꽉 채운다 → 박스 ≈ 잉크
- 라틴 대문자는 캡높이~베이스라인만 채운다 → **박스 ≫ 잉크** (디센더 공간이 빔)

따라서 박스를 맞추면 잉크는 어긋난다. 특히 **라틴 대문자는 디센더가 없어
캡 덩어리가 줄상자 위쪽에 앉는다.**

### 실제로 잰 것 **[측정]**

제호(라틴 대문자 64px) + 양옆 귀(한글 12px 2줄) 정렬 시안 7가지의 잉크 중심 편차:

| 시안 | 편차 |
|---|---|
| `align-items: end` | −10.14px |
| `align-items: last baseline` | −8.73px |
| `text-box: cap alphabetic` | −9.41px |
| `align-items: center` + 패딩 0 | −4.53px |
| **`center` + 광학 보정 9px** | **−0.03px** ✓ |

**교훈:** 어떤 CSS 정렬 키워드도 혼식에서 자동으로 맞춰주지 않는다.
**재고, 남은 편차는 광학 보정값으로 흡수하고, 그 값에 주석으로 근거를 남긴다.**
`text-box-trim` 같은 신규 속성도 만능이 아니다(여기선 오히려 나빴다).

### 자간의 부작용 두 가지 **[경험]**

1. **`letter-spacing`은 마지막 글자 **뒤에도** 붙는다.**
   - 가운데 정렬한 트래킹 텍스트는 잉크가 왼쪽으로 밀린다
   - 밑줄(`::after`)이 글자보다 길어진다 → `right: .14em`으로 당겨야 한다
2. **기하학적 중심 ≠ 광학적 중심.**
   실제 사례: 줄 전체는 중심 오차 0.00px였는데 "안 맞아 보인다"는 지적이 맞았다.
   줄 안에서 **유일하게 강한 마크(적색 밑줄)가 중심에서 16px 왼쪽**에 있었기 때문.
   → 눈은 가장 강한 마크로 중심을 잡는다. **무게가 어디 쏠렸는지를 봐야 한다.**

### 고치지 말아야 할 것 **[판단]**

한 줄에 한글과 모노 대문자가 나란히 있으면 잉크 중심이 ~1px 다르다.
**이건 정상이다.** 베이스라인은 맞아 있고, 차이는 한글의 잉크가 더 높기 때문이다.
중심을 억지로 맞추면 베이스라인이 틀어진다.

## 6. 측정 길이·기타

- **한 줄 글자 수**: 인쇄 본문 기준 40~60자 **[출처]**. 웹은 더 짧게 잡는 편이 낫다 **[판단]**
- **숫자**: `font-variant-numeric: tabular-nums`
- **줄바꿈 품질**: 문단은 `text-wrap: pretty`, 2~3줄짜리 짧은 덩어리는 `balance` **[경험]**
- **대비**: 한글 명조는 획이 가늘어 같은 색상값에서도 라틴보다 약해 보인다.
  회색 본문은 특히 위험하다. 계산해서 4.5:1을 확보할 것 **[경험]**
  (이 프로젝트에서 `#79808c`가 3.49:1로 AA 미달이었고 **링크에도** 쓰이고 있었다)

## 7. 진단 방법 — 감으로 고치지 않는다

"어색하다"는 피드백을 받으면 순서가 있다. **[경험]**

### 7-1. 잉크 측정

`design/tools/measure-ink.js` — 콘솔에 붙여넣고 실행.
`Range` + 높이 0인 `inline-block`으로 **실제 베이스라인**을 얻고,
Canvas `TextMetrics.actualBoundingBox*`로 **실제 잉크 범위**를 얻는다.
박스가 아니라 잉크를 재는 게 핵심.

폰트별 em 대비 잉크 비율도 이걸로 잰다:
```js
cx.font = '700 100px "Old Standard TT"';
const m = cx.measureText("THE RABBIT HOLE");
// m.actualBoundingBoxAscent / 100 = 캡높이 비율
```

### 7-2. squint test

렌더를 블러 처리해서 위계가 읽히는지 본다. 헤드리스 크롬 스크린샷을
`filter: blur(7px) grayscale(1)` 건 페이지에 넣고 다시 찍으면 된다.
**흐렸을 때 1순위·2순위·그룹이 구분되지 않으면 위계가 없는 것이다.**

### 7-3. 값 분포 세기

CSS에서 `font-size` / `line-height` / 간격의 **고유값 개수**를 센다.
이 프로젝트 v8: font-size 19개, 간격 23개(4px 배수 아닌 값 12개).
역할은 4단인데 값이 19개면 **그건 스케일이 아니라 노이즈다.**
특히 9.5/10/10.5/11.5/12/12.5px처럼 4px 폭에 몰린 값들은
보이지도 않으면서 아무 일도 안 한다.

### 7-4. 순서

레퍼런스 서치 → 잉크 측정 → squint test → 값 분포 → **그 다음에** 고친다.
측정 전후 수치를 같이 남긴다(19개 → 5개). 그래야 개선을 확인할 수 있다.

## 8. 안티패턴 목록 (빠르게 훑을 것)

- [ ] `word-break: keep-all`과 `overflow-wrap: break-word`를 같이 걸었다
- [ ] `.la` / `.mo` 같은 라틴 유틸리티 클래스 안에 한글이 들어가 있다
- [ ] 한글 폰트가 폰트 스택 맨 앞에 있다 (라틴이 두 종류로 그려진다)
- [ ] `palt`를 body 전체에 걸었다
- [ ] 제목 행간이 라틴 기준값(1.1~1.3)이다
- [ ] 폰트를 바꿨는데 자간 토큰을 그대로 뒀다
- [ ] 혼식 라틴에 광학 보정(105%)이 없다
- [ ] `align-items`로 혼식 정렬을 맞췄다고 생각하고 재보지 않았다
- [ ] 트래킹 준 텍스트를 가운데 정렬하고 밑줄을 그었다 (`right` 보정 없음)
- [ ] 회색 한글 본문 대비를 계산하지 않았다
- [ ] font-size 고유값이 역할 수보다 3배 이상 많다

---

## 검증 안 된 것 — 스킬로 만들기 전에 확인할 것

1. **브라우저**: 전부 Chrome(헤드리스)에서만 쟀다. Safari·Firefox에서 잉크 위치와
   `overflow-wrap` 동작이 같은지 확인 안 됨.
2. **폰트 일반화**: 0.73em / 0.945em은 **Old Standard TT와 Nanum Myeongjo의 값**이다.
   다른 조합에서도 "한글이 ~30% 커 보인다"가 성립하는지는 미확인.
   명조/고딕, 세리프/산세리프 조합별로 표가 필요하다.
3. **`--mh-optical: 9px`** 같은 광학 보정값을 **공식으로 유도할 수 있는지** 미해결.
   지금은 매번 재는 수밖에 없다. (디센더 비율에서 유도해봤으나 안 맞았다)
4. **세로쓰기, 루비, 한자 병기** 전혀 다루지 않음.
5. **가변폰트**의 optical size 축이 한글에서 어떻게 작동하는지 미확인.
6. `text-box-trim` / `text-box-edge`의 한글 동작 — 한 번 써봤고 결과가 나빴는데
   왜 나빴는지 원인 규명 안 함.

## 스킬로 만들려면 더 필요한 것

- **발동 조건**: `lang="ko"` 문서, 한글이 든 CSS/HTML 편집, "조판/타이포그래피" 언급 등
- **범위 결정**: 진단 전용인가, 수정까지 하는가
- **폰트 조합별 보정 표**: 최소 3~4쌍은 재서 넣어야 재사용 가치가 생긴다
- `measure-ink.js`를 스킬 번들 스크립트로 포함
